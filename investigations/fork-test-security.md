# Fork surface-test security investigation

## Scope and evidence

This review is pinned to [commit `7a3e37b29bd17f91f3cd0f854a3508a11d9776fb`](https://github.com/github/actions-migrations-via-copilot/tree/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb), the public suite named in the issue. The local branch is `copilot/investigate-fork-test-isolation` at `c090108`, not that commit; findings below refer to the pinned public files, not an assumption that the two trees are identical. The checked-out workflow has the same relevant job flow.

## Confirmed findings

- **A reviewed SHA is not isolation.** A fork `pull_request` sets `target.run=false`, so the credentialed test jobs do not start automatically. A manual dispatch with a PR number requires a full SHA and checks that it is still that PR's current head (`surface-tests.yml`, [lines 59–93](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L59-L93)). This prevents a stale/mistyped SHA, but deliberately allows that exact commit to run.
- **Fork-controlled code shares a job with credentials.** Both test jobs check out the selected SHA with `persist-credentials: false` (`surface-tests.yml`, [lines 95–117](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L95-L117), [139–173](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L139-L173)). The CLI job executes scripts from that checkout with `github.token` and `copilot-requests: write`; VS Code executes its scripts with `COPILOT_GITHUB_TOKEN` when configured. Disabling checkout's persisted Git credentials does not prevent code in the job from reading credentials explicitly passed to its process.
- **Sanitization is not a security boundary.** The artifact sanitizer is also checked out from the selected commit and receives the respective token (`surface-tests.yml`, [lines 118–128](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L118-L128), [174–185](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L174-L185)). Its redaction logic ([`sanitize_artifacts.py`](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/tests/surfaces/sanitize_artifacts.py)) cannot protect credentials from code that controls the sanitizer or ran before it.
- **No shared cache path is visible in this workflow.** The pinned workflow has no cache restore/save action or cache option on `setup-node`; the upload/download-artifact steps pass run-specific evidence to the results job. The results job checks out the selected commit and runs its `summarize.py` against those artifacts ([lines 187–217](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L187-L217)). Thus PR-controlled code can influence its own report, but this file alone does not establish poisoning of a trusted cross-run cache.
- **The status writer has a separate boundary.** `pr-status` does not check out or run PR code. Its only explicit permission is `statuses: write`, and its inline command writes a status to the SHA selected and checked by `target` ([lines 219–234](https://github.com/github/actions-migrations-via-copilot/blob/7a3e37b29bd17f91f3cd0f854a3508a11d9776fb/.github/workflows/surface-tests.yml#L219-L234)). The result it reports is nevertheless produced by the PR-controlled test/results path.

## Risk versus assumptions

**Reachable risk:** when an authorized actor manually starts a fork run, code at the reviewed commit runs in token-bearing jobs. A malicious or compromised commit could use the credentials available to those processes and could emit misleading artifacts/results. The SHA check confirms which code is run; it does not make that code safe.

**Not established by the reviewed workflow:** a route to a shared trusted cache, or access to credentials beyond the permissions/secret explicitly available to each job. The actual configured scope of `COPILOT_GITHUB_TOKEN`, who can dispatch this workflow, and the precise CodeQL dataflow are not established here. The issue reports a HIGH CodeQL cache-poisoning alert at this workflow; the alert API was inaccessible during this review (403), so the alert is not dismissed or independently reclassified.

## Smallest safe next step

If fork code is not to be trusted with Copilot credentials, the smallest safe policy change is to stop the manual fork path before the credential-bearing CLI and VS Code jobs (retain offline tests that do not execute PR code). There is no sanitizer-only or SHA-only change that makes arbitrary PR code safe to run with those credentials. If maintainers need credentialed fork tests, they must explicitly accept that reviewed code is being granted the job's available credentials; that is an execution trust decision, not isolation.

For the CodeQL alert, inspect its exact trace and confirm whether it reaches a cache restore/save sink. If no such sink exists, document that trace-based disposition rather than suppressing the alert by assumption.

**Smallest regression check:** an offline workflow test should feed a fork `pull_request` event and assert that the credential-bearing jobs are skipped; separately assert no cache restore/save is introduced on this path. Before any policy change, maintainers must decide whether credentialed manual fork tests are still required and whether that trust grant is acceptable.
